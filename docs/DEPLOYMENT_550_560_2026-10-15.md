project rule is that canonical schema changes on the shared Supabase database
are the schema owner's to run, and the plan requires the isolated test first.
Everything below has been run and verified on isolated local databases.

## Order of application

Both files begin with `BEGIN;` and end with `COMMIT;`, so each applies as one
transaction: it either lands completely or not at all. Run them as the schema
owner, from the backend checkout.

### 0. Connect without putting a password on the command line

Put the connection in a `.pgpass` file (`host:port:database:user:password`,
one line), then point psql at it. Never pass `PGPASSWORD` and never paste a
connection string that contains the password.

```bash
export PGPASSFILE="$HOME/.pgpass" PGSSLMODE=require
```

```bash
export PGHOST=<supabase-host> PGPORT=5432 PGDATABASE=postgres PGUSER=<owner-role>
```

### 1. Back up, and confirm you can restore

Take a snapshot immediately before applying, and confirm point-in-time restore
is available for this project. Do not continue without it.

### 2. Check the database is at migration 540 and that 550/560 are not applied

```bash
psql -c "SELECT to_regclass('actor_update_subscription') AS needs_540_present, to_regclass('actor_update_subscription_run') AS must_be_null_550, to_regclass('collection_request') AS must_be_null_550;"
```

```bash
psql -c "SELECT count(*) AS must_be_zero_560 FROM information_schema.columns WHERE table_name='actor_verification_event' AND column_name='decision_origin';"
```

### 3. Apply the two migrations, in order

`-v ON_ERROR_STOP=1` makes psql stop and roll back on the first error.

```bash
psql -v ON_ERROR_STOP=1 -f C:/Users/Ismail/Projects/GHUS-Platform/agents/sql/550_v2_discovery_requests.sql
```

```bash
psql -v ON_ERROR_STOP=1 -f C:/Users/Ismail/Projects/GHUS-Platform/agents/sql/560_v2_agent_auto_verification.sql
```

### 4. Verify

```bash
psql -c "SELECT to_regclass('actor_update_subscription_run') AS run_table, to_regclass('collection_request') AS request_table, (SELECT count(*) FROM pg_constraint WHERE conname='ck_actor_verification_event_origin') AS origin_constraint;"
```

```bash
psql -c "SELECT decision_origin, count(*) FROM actor_verification_event GROUP BY 1 ORDER BY 1;"
```

Expected: both tables present, the constraint present, and every existing
verification reading `ghus_review` or `existing_canonical_migration`.
`agent_auto_accept` must be **0** before any agent run.

### 5. Deploy both applications together

The frontend reads the new columns, so the platform and the backend go out in
the same deployment.

## Rollback

In reverse order — 560 first, then 550:

```bash
psql -v ON_ERROR_STOP=1 -f C:/Users/Ismail/Projects/GHUS-Platform/agents/sql/rollback/560_v2_agent_auto_verification.sql
```

```bash
psql -v ON_ERROR_STOP=1 -f C:/Users/Ismail/Projects/GHUS-Platform/agents/sql/rollback/550_v2_discovery_requests.sql
```

**Neither rollback deletes anything — both refuse instead.**

- 560's rollback **raises an exception** if any `agent_auto_accept`
  verification exists ("append-only"), then restores the two-origin
  constraint.
- 550's rollback **raises an exception** if any request was made from the
  Discovery page, or any `biweekly` cadence is in use: *"a rollback never
  deletes a request"*. Cancel or migrate those requests first. It then
  restores the 540 constraints and drops the three columns 550 added
  (`title`, `focus_terms`, `max_new_actors_per_run`).

So if either rollback errors, that is the design working: something now depends
on what the migration allowed, and it is telling you to deal with that first
rather than losing it.

## Person discovery

Supervisor sign-off was confirmed on 2026-10-15 and recorded in
`TARGETING_POLICY.md` section 6, so `people_enabled` is now `true` in
`agents/config/sources.yaml`. Neither 550 nor 560 is involved: the flag is

What it does **not** change: person records are never auto-created and never
auto-absorbed — every one routes to human review, enforced in `promote()` —
and only the professional fields section 6 permits are collected.

## Automatic verification is OFF until GHUS confirms it

`actor_auto_accept_status: verified` in `agents/config/sources.yaml` is not
enough on its own. Since 2026-10-15 the run also requires the environment
variable:

```
GHUS_AGENT_AUTO_VERIFY=confirmed
```

Without it, accepted actors are created **Parked** with a `verify_actor` review
item, exactly as before 560, and the run records
`actor_auto_verify_disabled` in its stats. Set it only in an environment where
GHUS has confirmed the policy.

Whatever that setting is, an agent-verified actor **cannot** authorise Deep
Pull: `actor_is_verified_for_topic` accepts only the latest `ghus_review`
decision for that exact actor and topic.
