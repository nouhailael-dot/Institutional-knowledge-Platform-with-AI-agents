# Deploying migrations 550 and 560 — procedure for the schema owner

Approved by the platform owner on 2026-10-15. **Not applied by Claude:** the
project rule is that canonical schema changes on the shared Supabase database
are the schema owner's to run, and the plan requires the isolated test first.
Everything below has been run and verified on isolated local databases.

## What the two migrations add

| Migration | Adds | Canonical writer |
|---|---|---|
| `agents/sql/550_v2_discovery_requests.sql` | `actor_update_subscription` request columns (`title`, `focus_terms`, `max_new_actors_per_run`, `requested_via`), `actor_update_subscription_run`, `collection_request` | `agents/collection/subscription_store.py` |
| `agents/sql/560_v2_agent_auto_verification.sql` | `actor_verification_event.decision_origin` (`ghus_review` / `existing_canonical_migration` / `agent_auto_accept`) + `migration_batch_id`, with `ck_actor_verification_event_origin` | `agents/enrichment/decisions.py` |

Rollbacks: `agents/sql/rollback/550_…sql` and `…/560_…sql` (29 rollback files in
total; asserted by `tests/db/test_architecture_v2_schema.py`).

## Order of application

1. **Back up first.** Point-in-time restore must be available, and take a
   snapshot immediately before step 3.
2. Confirm the database already carries migration 540
   (`to_regclass('actor_update_subscription')` is not null).
3. Apply `550_v2_discovery_requests.sql`, then `560_v2_agent_auto_verification.sql`,
   each in its own transaction, as the schema owner.
4. Verify:
   ```sql
   SELECT to_regclass('actor_update_subscription_run'),
          to_regclass('collection_request');
   SELECT conname FROM pg_constraint
    WHERE conname = 'ck_actor_verification_event_origin';
   SELECT decision_origin, count(*) FROM actor_verification_event GROUP BY 1;
   ```
   Every existing event must read `ghus_review` or
   `existing_canonical_migration`; `agent_auto_accept` must be 0 before any
   agent run.
5. Deploy both applications **together** (frontend reads the new columns).

## Rollback

Apply `agents/sql/rollback/560_…sql` then `550_…sql`, in that order. Both are
reversible: 550 drops tables and columns it added; 560 drops the two columns
and the check constraint. No historical row is deleted by either.

## Automatic verification is OFF until GHUS confirms it

`actor_auto_accept_status: verified` in `agents/config/sources.yaml` is not
enough on its own. Since 2026-10-15 the run also requires the environment
variable:

```
GHUS_AGENT_AUTO_VERIFY=confirmed
```

Without it, accepted actors are created **Parked** with a `verify_actor` review
item, exactly as before 560, and the run records
`actor_auto_verify_disabled` in its stats. Set it only in an environment where
GHUS has confirmed the policy.

Whatever that setting is, an agent-verified actor **cannot** authorise Deep
Pull: `actor_is_verified_for_topic` accepts only the latest `ghus_review`
decision for that exact actor and topic.
