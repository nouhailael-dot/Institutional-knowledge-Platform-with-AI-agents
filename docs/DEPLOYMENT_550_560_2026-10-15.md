project rule is that canonical schema changes on the shared Supabase database
are the schema owner's to run, and the plan requires the isolated test first.
Everything below has been run and verified on isolated local databases.

## Order of application

Both files begin with `BEGIN;` and end with `COMMIT;`, so each applies as one
transaction: it either lands completely or not at all. Run them as the schema
owner, from the backend checkout.

## Running it from PowerShell on Windows

The owner applies these from their own PowerShell session. Every command below
is PowerShell, not bash: `$env:NAME = "value"`, and `;` rather than `&&`.

**The password lives in `%APPDATA%\postgresql\pgpass.conf`** — on Windows libpq
reads that file, not `~/.pgpass`. One line,
`host:port:database:user:password`, with `\` escaping any `:` or `\` inside the
password itself:

```powershell
New-Item -ItemType Directory -Force "$env:APPDATA\postgresql" | Out-Null
Set-Content -Path "$env:APPDATA\postgresql\pgpass.conf" -Value "HOST:5432:postgres:USER:PASSWORD" -Encoding ascii
```

**Session setup.** Use the direct connection on **5432**, never the transaction
pooler on 6543:

```powershell
$env:Path = "C:\Program Files\PostgreSQL\17\bin;" + $env:Path
$env:PGHOST = "db.<project-ref>.supabase.co"
$env:PGPORT = "5432"
$env:PGDATABASE = "postgres"
$env:PGUSER = "postgres"
$env:PGSSLMODE = "require"
$env:PGPASSFILE = "$env:APPDATA\postgresql\pgpass.conf"
psql -Atc "SELECT current_database() || ' as ' || current_user;"
```

**Pre-check — this one decides whether you may continue:**

```powershell
psql -Atc "SELECT 'cadence_530=' || (SELECT count(*) FROM information_schema.columns WHERE table_name='collection_run' AND column_name='cadence') || ' subscription_540=' || (to_regclass('actor_update_subscription') IS NOT NULL) || ' run_table_550=' || (to_regclass('actor_update_subscription_run') IS NOT NULL) || ' request_table_550=' || (to_regclass('collection_request') IS NOT NULL) || ' decision_origin_560=' || (SELECT count(*) FROM information_schema.columns WHERE table_name='actor_verification_event' AND column_name='decision_origin');"
```

- `cadence_530=1` and `subscription_540=true` → go on.
- `cadence_530=0` → **stop.** 550 will fail without it, and 530 is a separate,
  much larger migration (327 lines; it creates `strategic_entity`,
  `person_verification_event` and several guard triggers) that is not covered
  by the 550/560 approval. Decide on 530 on its own terms first.
- `run_table_550=true` or `decision_origin_560=1` → that migration is already
  applied. Both files are safely re-runnable, so applying again is harmless.

**Record the before-state**, to compare afterwards:

```powershell
psql -Atc "SELECT 'actors=' || (SELECT count(*) FROM actor) || ' verifications=' || (SELECT count(*) FROM actor_verification_event);"
```

**Apply, one at a time.** Each file is a single transaction and
`ON_ERROR_STOP=1` makes psql abort on the first error, so a failure leaves
nothing behind:

```powershell
psql -v ON_ERROR_STOP=1 -f "C:\Users\Ismail\Projects\GHUS-Platform\agents\sql\550_v2_discovery_requests.sql"
if ($LASTEXITCODE -eq 0) { "550 applied" } else { "550 FAILED - nothing was committed" }
```

```powershell
psql -v ON_ERROR_STOP=1 -f "C:\Users\Ismail\Projects\GHUS-Platform\agents\sql\560_v2_agent_auto_verification.sql"
if ($LASTEXITCODE -eq 0) { "560 applied" } else { "560 FAILED - nothing was committed" }
```

**Verify:**

```powershell
psql -Atc "SELECT 'run_table=' || (to_regclass('actor_update_subscription_run') IS NOT NULL) || ' request_table=' || (to_regclass('collection_request') IS NOT NULL) || ' origin_constraint=' || (SELECT count(*) FROM pg_constraint WHERE conname='ck_actor_verification_event_origin') || ' new_columns=' || (SELECT count(*) FROM information_schema.columns WHERE table_name='actor_update_subscription' AND column_name IN ('title','focus_terms','max_new_actors_per_run'));"
psql -Atc "SELECT decision_origin || '=' || count(*) FROM actor_verification_event GROUP BY 1 ORDER BY 1;"
psql -Atc "SELECT 'actors=' || (SELECT count(*) FROM actor) || ' verifications=' || (SELECT count(*) FROM actor_verification_event);"
```

Expected: `run_table=true request_table=true origin_constraint=1
new_columns=3`; only `ghus_review` and `existing_canonical_migration` origins,
**no `agent_auto_accept`**; and the actor and verification counts unchanged
from the before-state.

**If you need to undo it** (reverse order, and both refuse rather than delete):

```powershell
psql -v ON_ERROR_STOP=1 -f "C:\Users\Ismail\Projects\GHUS-Platform\agents\sql\rollback\560_v2_agent_auto_verification.sql"
psql -v ON_ERROR_STOP=1 -f "C:\Users\Ismail\Projects\GHUS-Platform\agents\sql\rollback\550_v2_discovery_requests.sql"
```

**Clear the session when you are done**, so a later command cannot reach
production by accident:

```powershell
Remove-Item Env:PGHOST, Env:PGPORT, Env:PGDATABASE, Env:PGUSER, Env:PGSSLMODE, Env:PGPASSFILE -ErrorAction SilentlyContinue
```

### 0. Connect without putting a password on the command line (bash equivalent)

Put the connection in a `.pgpass` file (`host:port:database:user:password`,
one line), then point psql at it. Never pass `PGPASSWORD` and never paste a
connection string that contains the password.

```bash
export PGPASSFILE="$HOME/.pgpass" PGSSLMODE=require
```

```bash
export PGHOST=<supabase-host> PGPORT=5432 PGDATABASE=postgres PGUSER=<owner-role>
```

### 1. Back up, and confirm you can restore

Take a snapshot immediately before applying, and confirm point-in-time restore
is available for this project. Do not continue without it.

### 2. Check the prerequisites, and whether 550/560 are already applied

**550 needs migration 530 as well as 540.** A rehearsal on 2026-10-16 found
this the hard way: on a database carrying 540 but not 530, 550 fails at line 68
with `ERROR: column "cadence" does not exist`, because it re-states a
constraint on `collection_run.cadence`, and that column comes from 530. The
failure is clean — the whole file is one transaction and rolls back — but it
stops the deployment.

```bash
psql -c "SELECT (SELECT count(*) FROM information_schema.columns WHERE table_name='collection_run' AND column_name='cadence') AS needs_530_one, to_regclass('actor_update_subscription') AS needs_540_not_null, to_regclass('actor_update_subscription_run') AS is_550_applied, to_regclass('collection_request') AS is_550_applied_too, (SELECT count(*) FROM information_schema.columns WHERE table_name='actor_verification_event' AND column_name='decision_origin') AS is_560_applied;"
```

Required before applying: the first column **1**, the second **not null**. If
`is_550_applied` / `is_560_applied` already show the objects, that migration is
in place — both files are safely re-runnable, so a repeat is harmless.

If `needs_530_one` comes back 0, apply 530 first:

```bash
psql -v ON_ERROR_STOP=1 -f C:/Users/Ismail/Projects/GHUS-Platform/agents/sql/530_v2_conformance_fixes.sql
```

### 3. Apply the two migrations, in order

`-v ON_ERROR_STOP=1` makes psql stop and roll back on the first error.

```bash
psql -v ON_ERROR_STOP=1 -f C:/Users/Ismail/Projects/GHUS-Platform/agents/sql/550_v2_discovery_requests.sql
```

```bash
psql -v ON_ERROR_STOP=1 -f C:/Users/Ismail/Projects/GHUS-Platform/agents/sql/560_v2_agent_auto_verification.sql
```

### 4. Verify

```bash
psql -c "SELECT to_regclass('actor_update_subscription_run') AS run_table, to_regclass('collection_request') AS request_table, (SELECT count(*) FROM pg_constraint WHERE conname='ck_actor_verification_event_origin') AS origin_constraint;"
```

```bash

```

Expected: both tables present, the constraint present, and every existing

`agent_auto_accept` must be **0** before any agent run.

The frontend reads the new columns, so the platform and the backend go out in

## Rollback

In reverse order — 560 first, then 550:

```bash
psql -v ON_ERROR_STOP=1 -f C:/Users/Ismail/Projects/GHUS-Platform/agents/sql/rollback/560_v2_agent_auto_verification.sql
```

```bash
psql -v ON_ERROR_STOP=1 -f C:/Users/Ismail/Projects/GHUS-Platform/agents/sql/rollback/550_v2_discovery_requests.sql
```

**Neither rollback deletes anything — both refuse instead.**

- 560's rollback **raises an exception** if any `agent_auto_accept`
  verification exists ("append-only"), then restores the two-origin
  constraint.
- 550's rollback **raises an exception** if any request was made from the
  Discovery page, or any `biweekly` cadence is in use: *"a rollback never
  deletes a request"*. Cancel or migrate those requests first. It then
  restores the 540 constraints and drops the three columns 550 added
  (`title`, `focus_terms`, `max_new_actors_per_run`).

So if either rollback errors, that is the design working: something now depends
on what the migration allowed, and it is telling you to deal with that first
rather than losing it.

## Person discovery

Supervisor sign-off was confirmed on 2026-10-15 and recorded in
`TARGETING_POLICY.md` section 6, so `people_enabled` is now `true` in
`agents/config/sources.yaml`. Neither 550 nor 560 is involved: the flag is

What it does **not** change: person records are never auto-created and never

and only the professional fields section 6 permits are collected.

## Automatic verification is OFF until GHUS confirms it

`actor_auto_accept_status: verified` in `agents/config/sources.yaml` is not
enough on its own. Since 2026-10-15 the run also requires the environment
variable:

```
GHUS_AGENT_AUTO_VERIFY=confirmed
```

Without it, accepted actors are created **Parked** with a `verify_actor` review
item, exactly as before 560, and the run records
`actor_auto_verify_disabled` in its stats. Set it only in an environment where
GHUS has confirmed the policy.

Whatever that setting is, an agent-verified actor **cannot** authorise Deep
Pull: `actor_is_verified_for_topic` accepts only the latest `ghus_review`
decision for that exact actor and topic.
